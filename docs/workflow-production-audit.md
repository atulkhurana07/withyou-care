# Workflow review and production release gates

Reviewed against PRD v2.0 and the companion design specification on 13 October 2026. The existing Next.js/Firebase and Flutter stack is retained. This review distinguishes implemented behavior, measured checks and unresolved release work. Passing a local test is not clinical validation or a production availability claim.

## Research applied

Invitation/recovery tokens follow [OWASP recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): unpredictable secrets, limited lifetime, single use and account-enumeration resistance. The recovery response is uniform; equivalent timing and distributed edge defenses still need production tests.

Firebase's [action-link documentation](https://firebase.google.com/docs/auth/admin/email-action-links) informs verification/reset links. [Firestore cursor guidance](https://firebase.google.com/docs/firestore/query-data/query-cursors) establishes the remaining pagination work; current bounded pilot behavior is not a large-clinic scale claim.

Flutter's [architecture recommendations](https://docs.flutter.dev/app-architecture/recommendations) informed extraction of the HTTP client from screen state. Its [accessibility checklist](https://docs.flutter.dev/ui/accessibility) informed semantic controls, large targets, error handling and a two-times text-scale test. This does not replace TalkBack/VoiceOver testing. [Offline-first guidance](https://docs.flutter.dev/app-architecture/design-patterns/offline-first) informed the deliberate choice to keep medical data in memory until encrypted caching and revocation behavior are designed.

Google's [Gemini terms](https://ai.google.dev/gemini-api/terms#unpaid-services) prevent sensitive/personal patient notes from going through the unpaid development path. Schema-valid extraction still requires local validation and clinician review. [Firebase messaging setup](https://firebase.google.com/docs/cloud-messaging/flutter/get-started) requires platform app configuration, consent and actual device checks; a working web preview is insufficient evidence of push delivery.

[PDF-lib custom fonts](https://pdf-lib.js.org/) informed Devanagari embedding instead of deleting characters. [Flutter Android release guidance](https://docs.flutter.dev/deployment/android) informed private keystore configuration and removal of debug signing for release builds.

## Verification and acceptance

New-organization integration tests exercise owner registration → persisted activation → own staff accounts → patient/encounter → doctor review/publication → recipient-bound patient account → authorized tasks/PDF. Negative checks cover wrong recipient, unauthorized staff management, consumed/revoked invitation and disabled staff access. Existing immutable-report, tenant/assignment, supersession and self-report checks remain.

The mobile UI uses the same backend. Flutter static analysis, widget checks and compiled-preview tests verify login, actual approved tasks, completion and care updates. Actual Android results and remaining release blockers are recorded in `docs/validation.md`; do not infer a signed production binary or notification delivery from a compiled web preview.

The production preflight intentionally fails in the running local environment. A positive preflight would establish configuration only. It is never a replacement for clinical sign-off, professional verification, consent/privacy decisions, monitored deployment, backup restoration, native device tests or the unimplemented features listed above.


Android local reminders follow the plugin's [platform setup and scheduling guidance](https://pub.dev/packages/flutter_local_notifications). The app uses Asia/Kolkata and inexact alarms, requests notification permission only after the patient chooses it, and schedules neutral messages rather than clinical instructions. Emulator confirmation is evidence of notification plumbing, not guaranteed future delivery or background freshness.
